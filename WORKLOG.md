- Симптом владельца: «скачивание аудио нормально не работает ни в мобильной, ни в полной версии; значок скачивания накладывается на элементы трека; сделай отдельной вкладкой, чтобы был весь функционал VK Music Player».
- **УБРАНО полностью**: JS-секция `AUDIO_DL_JS` (кнопки «↓» в страницах VK — источник наложения на элементы), тумблер «Кнопки скачивания у треков», `AudioGrabber`, `VkbBridge.downloadAudioTrack`. Страницы VK больше не трогаются вовсе.
- **НОВАЯ вкладка «Музыка»** (кнопка-нота на нижней панели, `music/MusicActivity` + `assets/music.html`, тёмная тема): собственный плеер ВНЕ страниц VK, по образцу VK Music Player от VK Next. Функционал: «Моя музыка» (audio.get, пачки по 50, бесконечный скролл), поиск (audio.search, дебаунс 400 мс), плейлисты (audio.getPlaylists → audio.get по album_id) с входом/выходом, обложки (album.thumb.photo_300), значки битрейта (~Nk, как в расширении), серые строки для ограниченных/DMCA треков. Плеер: play/pause/next/prev, seek, шаффл (Фишер–Йетс с выводом текущего трека вперёд), повтор (выкл/все/один), тайминги, обложка в нижней панели. Скачивание: у каждого трека кнопка «⤓» В НАШЕМ UI (страницы VK не затрагиваются) — mp3 в «Загрузки» через DownloadManager, HLS — сегменты в один .ts в «Загрузки» (MediaStore на Android 10+, файл на 8–9; конвертации в mp3 нет — её у VK Next делают ffmpeg.wasm/сервер; .ts играют VLC/MX Player).

- **HLS в WebView**: hls.js 1.5.20 (light, BSD) в assets; CORS для XHR-сегментов открывает `shouldInterceptRequest` — `Access-Control-Allow-Origin:*` ТОЛЬКО к ответам аудио-CDN (vkuser.net/vkuseraudio.ru/userapi.com/okcdn.ru/...) — эквивалент DNR-правила 8 расширения; остальное насквозь.

Теперь на `onStart` служба глушится только когда ничего не играет (`PlaybackService.isPlaying()`). (2) Служба держит СВОЙ частичный wake-lock (`PikoVK:playbackSvc`) ровно пока живёт — CPU больше не зависит от жизненного цикла активити (раньше lock держал только `MainActivity.onStop`, а вкладка живёт поверх MainActivity). (3) Рендереру вкладки запрещено «списывание» в невидимости — `setRendererPriorityPolicy(IMPORTANT, false)` (раньше true, как в браузере). (4) Тап по медиа-карточке теперь открывает саму вкладку «Музыка» (`attachMusicTab`/`fromMusicTab`), а не браузер поверх плеера — раньше это выглядело как полный сброс.
- Фикс фона №2 — ПОЛНЫЙ АУДИТ МЕХАНИЗМОВ ВЫЖИВАНИЯ (жалоба повторилась после первого фикса: «не в фоне ни при блокировке экрана музыка не продолжает работать, хотя уведомления включены»). Пересчитаны все механизмы Android 12-16: кэш-фризер (лечится FGS), фантомный киллер рендереров (лечится FGS + обработчик смерти рендерера), требования FGS mediaPlayback 14-16 (тип в манифесте + разрешения + старт из видимого состояния — всё было), Doze (FGS даёт сеть без ограничений), OEM-убийцы (вне кода). Найдены и закрыты 3 пробоины + 2 страховки:
  1. **`MainActivity.onDestroy` безусловно глушил `PlaybackService`** — главный убийца. Вкладка «Музыка» лежит ПОД MainActivity, систему ничего не обязывает хранить остановленную активити: при блокировке/сворачивании память или прошивка УНИЧТОЖАЮТ MainActivity → onDestroy → `PlaybackService.stop()` → процесс в кэш → заморозка за ~10 с → фантомный киллер добивает рендерер: звук обрывается, вкладка сбрасывается. Теперь служба/lock/ссылка гасятся только если звук НЕ вкладки «Музыки» (`fromMusicTab && isPlaying`).
  2. **В `MusicWebClient` не было `onRenderProcessGone`** — смерть рендерера без обработчика валит ВЕСЬ процесс приложения (документированное поведение WebView). В браузере обработчик был (`VkWebViewClient:360`), во вкладке забыли. Добавлен: `return true` + тихая пересборка вкладки (сборка WebView вынесена в `buildPlayerWebView`, как `buildWebView` в MainActivity), репорт «не играет» в шторку, лог `PikoVK-Music`. Очередь плеера восстанавливаться не может (живёт в JS страницы) — но приложение больше не «скидывается».
  3. **«Кража» ссылки шторки**: `MainActivity.onStart` и `buildWebView` прикрепляли браузерный WebView безусловно — пересоздание MainActivity поверх играющей вкладки уводило команды шторки в браузер и сбрасывало `fromMusicTab`. Оба места защищены проверкой `!PlaybackService.fromMusicTab`.
  4. **Страховка `MusicActivity.onStop`**: если играет, а службы нет (MainActivity уже уничтожена — упреждение моста и добор из её onStop не сработали), вкладка сама поднимает FGS + wake-lock в момент ухода с экрана (внутри grace-окна «переход из видимого состояния»).
  5. **Страховка от тихой демотации FGS** (`PlaybackService`): полевые репорты — часть прошивок через десятки минут молча снимает у FGS статус переднего плана; процесс в кэш → заморозка → звук. Пока играет, служба раз в минуту заново утверждает `startForeground` (`assertForeground`, `ServiceCompat` с типом mediaPlayback; это не «старт из фона» — служба уже жива), плюс немедленно при возврате к игре в `refreshMeta`. Fail-open.
  6. **Подмена видимости продублирована на уровне диспетчера**: `PlaybackWebView.dispatchWindowVisibilityChanged` — на части прошивок сигнал доходит только по цепочке dispatch от корня, минуя onWindowVisibilityChanged.

- **ОЧЕРЕДЬ ПЕРЕЕХАЛА В СЛУЖБУ** (жалоба после нативного плеера: «аудио работает, но треки вперёд не переключаются как при нажатии кнопки, так и после завершения»). Воспроизведено на стенде (headless-браузер + мок моста): после пересоздания вкладки (закрыл → открыл с карточки, смерть рендерера, убийство активити системой) страница СВЕЖАЯ, `syncPlayer` подтягивает из службы текущий трек, но очередь страницы ПУСТА (жила в JS и умирала вместе с WebView — это даже было задокументировано комментарием в MusicActivity) → кнопка «⏭» и автопереход молча ничего не делают; next/prev шторки без вкладки тоже не работали (pageJs в пустоту). Решение — очередь как у настоящих плееров, в самой службе:
  - **PlaybackService**: очередь хранится в companion (`queueTracks`/`queueOrder` JSON + `orderPos`/`queueIndex`/`queueShuffle`/`queueRepeat`, касание только с main); страница один раз отдаёт список играбельных треков и номер (`nativeQueue {tracks,index,shuffle,repeat}` — старт службы с упреждением, как nPlay); **авто-переход по завершению/ошибке делала сама служба** (`onCompletion/onError → handler.post shiftQueue(1,true)` — release плеера из его же колбэка через post; `errStreak` против вечного цикла битых ссылок), правила: repeat=one → рестарт, repeat=all → по кругу, default → пауза на конце; **next/prev шторки/гарнитуры** — напрямую в очередь (`dispatch`), без вкладки; prev — с откатом в начало трека (>3 с); шаффл — Фишер–Йетс в `rebuildOrder` (текущий первым), порядок живёт в `queueOrder`; пустой url в очереди трактуется как битая ссылка (шаг дальше); смена трека пушит полную карточку в вкладку (`pushState` → kind:'player' + cover + режимы — свежая вкладка оживает целиком); `__vkbMusicPos` получил 5-й аргумент rawId; пустая очередь next/prev — fallback в старый хук страницы (VK-страницы не тронуты).

## 2026-11-11 — доработка-10: кнопка «Поделиться» у видео
- Репорт владельца: «не могу поделиться видео при нажатии на кнопку поделиться». Две причины, обе — ограничения WebView, обе закрыты:
- **navigator.share не реализован в Android WebView** (Web Share API отсутствует): VK проверяет `typeof navigator.share === 'function'` и по провалу молча ломает кнопку. Добавлен шим SHARE_JS (ExtensionEngine, внедряется document-start всегда, без тумблера): если нативного API нет — `navigator.share`/`navigator.canShare` мостом `VkbBridge.share(text,url)` → системный chooser Android (ACTION_SEND, текст+ссылка). На Chrome с нативным API шим не перетирает его (typeof-проверка).
- **Окна VK игнорировались**: «Поделиться» в полной версии открывает vk.ru/share.php через window.open (и часть диалогов — target=_blank); `setSupportMultipleWindows` не включался, `onCreateWindow` не было — окно молча не открывалось. Теперь: `setSupportMultipleWindows(true)` + `javaScriptCanOpenWindowsAutomatically=true` (открывается и без жеста — fail-open) + `VkWebChromeClient.onCreateWindow/onCloseWindow` → `MainActivity.openPopupWindow/closePopup`: одно активное окно — тёмный оверлей с панелью «✕ Закрыть» и WebView (PlaybackWebView, настройки/шим расширений/мост VkbBridge/сторонние куки; упрощённый WebViewClient — смерть рендера закрывает окно; window.close закрывает сам). «Назад» при открытом окне закрывает окно (полный экран приоритетнее), любая пересборка WebView закрывает окно.
- Проверки: SHARE_JS синтаксис (node --check) + поведение (установка при отсутствии API, передача text/url в мост, вызов без text) — OK; check_piko_1323.py OK. Компиляция — владельцем.
